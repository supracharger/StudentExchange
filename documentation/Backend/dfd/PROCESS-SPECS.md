# Process specifications

These specifications complement the DFD arrows with transformation rules. They do not add new boundary data. A numbered process is a logical responsibility and can span source modules. Data-flow position and numbering do not imply execution timing. Error/result variants are part of each package in `DATA-DICTIONARY.md`.

## 1.0 — Present marketplace previews

**Input:** browse criteria, draft text/offer amount, bundled catalog and current local conversation. **Output:** filtered cards/detail views, local preview strings and updated conversation state.

- **1.1 Filter sample catalog:** normalize query by trim/lowercase; combine category matching with a text match over title, school and category. Output matching cards or an empty-state view.
- **1.2 Prepare listing detail:** resolve selectedListingId against the imported samples and project its title, price, category, school and condition. Pass selected listing context to message/offer preview transformations. Seller information is unavailable.
- **1.3 Append message preview:** accept nonblank trimmed draft text, append it to the App-level strings and clear the input. Empty text produces no append. It does not send a network message.
- **1.4 Append offer preview:** parse Number(offerAmount); accept only finite values greater than zero, format a two-decimal dollar amount, append `Offer: $...`, close the offer form and clear its amount. Invalid values do not append. UI input constraints are additional browser validation, not a payment-processing rule.

The four transformations are cohesive stopping points. A seller, conversation service, payment processor or order store would introduce unsupported new external information and is excluded. The local conversation is not partitioned by listing and is lost on reload/unmount.

## 2.0 — Manage accounts and website sessions

**Input:** account operation packages, account/school references, token eligibility, local sessions and access assessment. **Output:** account results, account/token/session mutations and operation-specific access data.

### 2.1 — Register account

1. **2.1.1 Assess registration access:** attach/assess the server-owned application/IP envelope. Return validation/service failures within registration result data rather than creating a record.
2. **2.1.2 Normalize fields and resolve school:** require email, names, password and school. Trim fields; lowercase email; title-format names. Require the configured email/name regex rules, an email ≤ 50 characters and a password of 8–50 allowed characters with at least one uppercase character and allowed symbol. Look up an existing exact full school name.
3. **2.1.3 Encode and store account:** deterministically encrypt email and password with their configured keys; persist names, school ID and Mountain timestamp. Unique-email insertion failure yields a conflict variant; other persistence failures yield error data.
4. **2.1.4 Project registration outcome:** return normalized email and creation notice, or the appropriate validation/conflict/service result. No token/session data is generated by this process.

### 2.2 — Authenticate and create session

1. **2.2.1 Compare credentials and admission:** normalize submitted email/password and compare their deterministic encrypted values with User records. Produce known-user evidence for login-specific attempt checks; do not treat a matched password as proof that an active block permits admission.
2. **2.2.2 Select or issue user token:** under the selected user's lock, reuse a token only when expiry is later than now plus one day. Otherwise generate/insert a token, with up to five attempts. Admin membership selects a 3-day lifetime; ordinary users receive 21 days. Reuse does not extend expiry. Block/service failures remain result alternatives.
3. **2.2.3 Project public profile:** obtain email, first_name, last_name and school. Explicit projection excludes password, token and future backend fields from browser-visible data. A missing/invalid profile does not establish a new local session.
4. **2.2.4 Rotate website session ID:** prune expired entries during login; reject capacity ≥ 5,000. Remove an existing browser session ID, create a 32-byte random opaque ID and map it to backend token plus fixed 12-hour expiry. Return the public profile and `se_session` cookie; never return the backend token to the browser.

Cookie attributes are `Path=/api`, HttpOnly, SameSite=Lax, 12-hour Max-Age, and Secure in production. They are the physical representation of the cookie result, not extra DFD control flow. The process-local Map is lost on restart and is not a shared multi-instance session store.

### 2.3 — Retrieve profile

Resolve the opaque cookie to an unexpired local session; forward its token in the backend's JSON request body; read and project the selected profile. A genuine expired/unknown visitor token can invalidate the local ID/cookie. An upstream transient failure does not itself prove that the user session expired. This read/projection is a cohesive primitive transformation and needs no additional layer.

### 2.4 — Update profile and read back

1. **2.4.1 Validate selected profile changes:** allow only email, first_name, last_name, school and password. Omitted/null/blank fields retain stored values; reject a request with no nonblank edit. Resolve current user and school data, normalize fields and assess access.
2. **2.4.2 Persist normalized changes:** write validated selected fields; duplicate normalized email is a conflict and does not commit partial profile changes. Profile/password updates do not revoke existing access tokens by themselves.
3. **2.4.3 Project saved profile outcome:** perform the separate normalized readback. A committed write plus failed read yields a successful saved notice with `profile:null`, not a failed-write claim or automatic second password write. A successful read yields the new public profile.

### 2.5 — Revoke user sessions

1. **2.5.1 Resolve logout identity:** derive selected identity from the website session and backend access assessment. Absent website sessions are an idempotent confirmation case; invalid app/IP data may still reject before backend token handling.
2. **2.5.2 Prepare token revocation:** for a valid selected identity, remove all backend token records for that user. Backend token-validation errors after application validation are masked with 200, so outcome data may be unconfirmed.
3. **2.5.3 Prepare local session removal:** after the adapter's accepted backend response, remove local entries sharing the visitor token and expire the cookie. Transport/service errors remain errors rather than pretending revocation was confirmed.
4. **2.5.4 Project logout confirmation:** produce a browser-safe notice with the appropriate qualification. HTTP success is not proof that any target token existed or was deleted.

### 2.6 — Publish school directory

Read Schools, project the exact lowercase `schools` property expected by the adapter, validate names and deduplicate the browser list. The backend public GET does not require user authorization; the configured adapter may still attach its server-owned forwarding envelope. Empty/invalid backend structures may produce safe service errors. Directory read/projection is a primitive operation.

## 3.0 — Manage administration

### 3.1 — Assess caller permissions

Read membership freshly for every admin operation through access assessment. Derive `manageAdmins` (> 0), `users/schools/profiles/deleteUsers` (≥ 10), `blocked` (≥ 20), `lockAdmins/viewAdminLevels` (≥ 30) and `endSessions` (any admin). Produce either a membership view or an operation-scoped request. A UI permission projection never substitutes for backend authorization. The backend user directory exposes levels at ≥ 27, but website projection withholds them until ≥ 30.

### 3.2 — Manage target user records

- **3.2.1 Resolve permitted target operation:** preserve caller identity and rank while selecting exact target email/ID. User listing/profile/deletion capabilities require caller ≥ 10. Target forwarding must pass shared hierarchy/lock checks. Unknown/blank selectors and forbidden targets yield error variants.
- **3.2.2 Project user management result:** join school and admin flags as appropriate; decrypt only intended email data and emit explicit public fields. Produce profile/directory or mutation confirmation results. A post-update read failure produces a saved/reload notice, not an instruction to repeat the write.
- **3.2.3 Persist target profile changes:** use the selected eligible user ID, validate and persist selected profile fields. Do not replace the caller's access token with the target's token.
- **3.2.4 Prepare target account deletion:** select the target user row for deletion and project the affected count/error. Schema-declared cascades are not drawn as guaranteed effects because actual foreign-key enforcement was not verified.

### 3.3 — Manage school records

Caller must be admin ≥ 10; backend rejects `to_user` forwarding. Read the directory, or create with nonblank name/short_name, or delete using a nonblank name and/or short_name selector. Apply the backend's title/space normalization and parameterized SQL behavior. Return a directory, mutation count/confirmation, validation error or safe service error. Separate read/create/delete variants are sufficiently defined in the data dictionary and route implementation without another diagram layer.

### 3.4 — Manage admin assignments

1. **3.4.1 Validate assignment fields:** require `to_user`; POST/PATCH require a nonnegative integer level below the caller's level. If locked is explicitly supplied, require caller ≥ 30 and value 0 or 1. Caller > 0 is required for assignment management.
2. **3.4.2 Assess target membership operation:** grant only to a nonadmin; change/remove only for an existing admin. Preserve lower-rank and locked-target restrictions already assessed by shared auth.
3. **3.4.3 Persist and project assignment:** insert/update/delete the selected Admins row and return target email plus operation-specific confirmation/error. Credentials and raw SQL errors are not added to browser result data.

### 3.5 — Inspect and clear attempts

1. **3.5.1 Validate attempt selectors:** require caller ≥ 20; reject backend user forwarding. Directory requests need no deletion selector. Clearing requires exactly one email or ip_addr, not both.
2. **3.5.2 Project attempt observations:** combine attempt rows with user names/emails and IP/user relationships. Include count/expiry without asserting every row is an active block. Project a clear result or validation/service error after removals.
3. **3.5.3 Prepare selected attempt removals:** resolve the selected user/IP and remove matching attempt rows. Report affected rows/not-found/error. Clearing attempts does not regenerate tokens revoked at threshold 10.

### 3.6 — Request target sign-out

Use caller token with `to_user`, not the target token. Where profile permission exists, the adapter checks target eligibility immediately before calling backend logout. Low-level admins receive a qualified result because backend logout may mask validation failures with 200. The result is a sign-out request confirmation, not certified revocation evidence.

## 4.0 — Prepare and assess access

This logical process collects related transformations spread across Node `api.mjs`, backend `AppAuthJson`, IP and Users helpers. It is not a new physical service. An operation discriminator selects applicable checks: public school reads, registration, login admission and token-authenticated operations do not all execute identical validation. Login attempt data is distinct from ordinary token validation.

### 4.1 — Prepare operation envelope

Resolve server-owned runtime settings and effective client IP; project allowlisted form fields; supply shared app credentials and the visitor token when required. Reject browser attempts to override protected envelope fields. At the adapter boundary, write requests require the expected same origin and valid bounded JSON. These rules transform request metadata into an accepted envelope/error package; they are not timing arrows.

### 4.2 — Establish service identity

- **4.2.1 Select service identity source:** use the cached service token when appropriate, or request configured service credential data for bootstrap/renewal. Concurrent login/renewal is coalesced by `loginPending`; promise mechanics are not data arrows.
- **4.2.2 Authenticate configured service user:** perform backend service login, selecting/issuing a token under the same backend token rules. Failure becomes safe unavailability data, without exposing configured credentials or invalidating an unrelated visitor session.
- **4.2.3 Verify and retain admin proof:** obtain Admin membership and require `is_admin:true` before retaining the service token in Node memory. Supply it as `admin_token` for IP forwarding. A backend explicit forwarding-expiry marker permits one renewal/retry because rejection precedes the operation; ordinary errors or saved-profile readback failure do not permit automatic replay.

### 4.3 — Assess application and IP data

- **4.3.1 Compare application credentials:** compare application credential data; validate forwarding token membership/expiry where forwarding is requested. Configured server identity and visitor identity remain separate.
- **4.3.2 Resolve effective IP identity:** resolve/register the connection IP and, when eligible, the forwarded visitor IP. Persist encrypted address data and select the effective IP ID. Do not treat arbitrary browser-supplied headers/body fields as trusted identity.
- **4.3.3 Assess IP attempt window:** read the selected IP's retained observation, transform count/expiry according to the configured policy, and update lock-use metadata. IP blocking does not revoke user tokens.
- **4.3.4 Project IP admission data:** emit application/IP context or a qualified rejection, including explicit forwarding-expiry markers where applicable. It produces data for the assessment transformation rather than branching the DFD into control states.

### 4.4 — Assess user and target data

- **4.4.1 Resolve caller credential evidence:** select an unexpired visitor token for token-based operations; use credential-match evidence for login admission. Resolve caller ID and admin membership. There is no Blocked_Users lookup in ordinary token validation itself.
- **4.4.2 Assess selected target scope:** forwarding requires an admin caller and exact stored target email; target must exist. An admin target must have strictly lower level; locked targets require caller ≥ 30. Preserve caller level and sudo_id while substituting target user.id and target isAdmin. An equal-rank check precedes the later self-forwarding allowance, so the allowance does not override that prohibition.
- **4.4.3 Transform user attempt window:** for login admission, create count 1 on first failure or -1 on a successful initial observation; set a five-minute window. Later evaluation treats negative count as zero. Failures increment; an active block also increments even with otherwise correct credentials. Count ≥ 10 blocks; transition to user count 10 removes all that user's tokens. At counts 20, 30, 40, ... extend expiry from `max(expiry, now)` by `5 minutes × max(count/10 − 2, 1)`. Successful requests before threshold do not reset count. Unknown login email has no user row to attach a user attempt record to.
- **4.4.4 Project resolved user context:** record successful selected user/IP association if applicable; output selected identity, original caller rank/ID, target status and operation-specific admission/error data.

### 4.5 — Publish access assessment

Project either account or admin assessment according to the operation family, preserving prepared envelope/resolved identity or qualified error fields. Safe adapter errors suppress upstream exception details and configured credential values; genuine visitor token expiry can map to 401, while target-rank rejection maps to forbidden scope rather than lost caller session. No new business data is synthesized here.

## 5.0 — Maintain security records

**5.1** selects token records older than the reference time and produces token removal data. **5.2** does the same for expired user-attempt records. **5.3** handles expired IP-attempt records. **5.4** selects stale process-local lock metadata according to the existing cleanup predicates.

These are primitive cohesive retained-record transformations. Clock evaluation belongs to the process specification; scheduler events are not extra DFD data packages. Current startup queues the delegate asynchronously without awaiting it, so cleanup can overlap host startup. `Maitenance` repeats it daily at 03:24 Mountain time. Cleanup does not initialize or migrate database tables. Session expiry is also handled in normal session lookup/login pruning; this process does not invent a shared durable session scheduler.

## 6.0 — Manage direct listings

**6.1 Retrieve listing records:** apply optional category predicate, join Listings.user_id to User.id and project listing fields plus joined user email/name. These fields reflect the current controller contract, not a claim that the website exposes a live seller contact feature.

**6.2 Create listing record:** accept Title, Description, Price, Category and supplied UserId; write parameterized values plus UTC ISO timestamp; return creation confirmation. The current controller does not perform shared authentication or ownership validation; the DFD does not invent those checks.

**6.3 Delete listing record:** select/mutate by path ID, derive the affected row outcome and return deletion confirmation or 404 not-found data. The logical stored-record input represents the selected data state from which the mutation result is derived, not an assertion that the controller issues a separate pre-read SQL statement.

These three operations are cohesive stopping points. G6/D14 indicate an expected table inferred from SQL, absent from the supplied DDL. The independent `../Data.db` connection and missing website listing route remain explicit implementation limitations. No authenticated seller, checkout, payment or order fulfillment is introduced.
